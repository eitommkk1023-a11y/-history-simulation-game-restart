## 接続した部分
1. 共通時計：dailyTickからpeopleDailyと軍事dayを同じclock.dayで更新。日・日スキップ・月・年・神モード一括進行が同じ経路を通る。月次側はpopulationAdvanced:trueで既に進めた30日を二重進行しない。旧peopleMonthlyの既定動作は維持。
2. 生活と軍務：serviceAvailabilityに月内の不在日数を記録し、生活側の労働・技能平均と自宅集落の食料需要へ反映。住民数や元の職業は複製/置換しない。外出中は自宅での仕事・訓練を実行しない。健康・加齢は既存の人口処理で進む。
3. 食事：既存の年齢・性別別必要量を日量にして実積荷から消費。自宅集落での同じ人物分の消費と重複させない。積荷不足は不足率として保存し、既存STARV_Hの式へ渡す。無料補充・新規物資・即死タイマーを追加しない。
4. 命令：到達記録→理解→実行依頼→実行結果を、同じ本編セーブ内の部隊/配送/取引結果へ接続。履歴にeventKeyを付け、保存された発行位置から再開する。
5. 描画：登録された伝令IDを候補へ重複なく追加し、伝令は生活用の周回位置と併存させず交通正本の座標を使う。一般の全NPCの実位置正本化を完了したものではない。
6. 本編セーブ：既存SAVE_FORMATと人口・集落・建築・民族・自然の保存を維持してmilitary拡張を追加。worldKey/checkpointId/day/seed/人口検査値で混在を拒否。JSONでは拡張内Map/Setを専用の単純データへ変換し、IndexedDBと同じ内容を保持する。
7. 読込：loadStateで候補を検証してからWorker生成へ進む。Worker結果に対する追加検証も世界交換前に行う。生成中は共通時計を停止し、失敗時は元の進行設定を戻す。旧セーブに軍事拡張がなければ空状態。人口のない最初期形式は元のpeopleNew移行経路を残す。

## 本編で見つかった再現性の原因
初回の本編試験では、同じ配送途中保存から再開しても人口検査値が不一致となった。人口側の交流候補リストP.membersが保存されず、死亡者等の削除待ち参照をロード時に除去していたため、候補の順序・乱数消費が変わっていた。

peopleSave/Loadに順序付きmembers/memberStartを追加し、人口を増やさず同じ参照列を復元するよう修正。未保存の旧形式は従来通り再構築する。修正後、新方式のセーブからの人口検査値・乱数・食料・軍事結果が本編で一致した。旧保存には元の参照順が無いため、過去の旧コードの推移まで完全再現できるとは扱わない。
